At a Glance ภาพรวมในแวบเดียว

Nelysia is an ergonomic, compiler-first TypeScript backend framework engineered for maximum speed and simplicity on both Node.js 22+ and Bun 1.4+, as well as Web Standard runtimes (Deno, Cloudflare Workers, Vercel). Designed with mechanical sympathy, Nelysia compiles route shapes ahead of time to eliminate middleware array iteration and context allocation overhead.

Nelysia คือ TypeScript Backend Framework สายพันธุ์ใหม่ที่ออกแบบด้วยปรัชญา Compiler-First เพื่อประสิทธิภาพสูงสุดบนทั้ง Node.js 22+ และ Bun 1.4+ ตลอดจน Web Standards (Deno, Cloudflare Workers, Vercel) โดยวิเคราะห์และปรับแต่งโครงสร้างเส้นทางล่วงหน้าแบบ Ahead-of-Time เพื่อขจัด Overhead ของ Context และ Middleware ให้เป็นศูนย์

src/app.ts
import { Nelysia, t } from "@narudom96/nelysia"

export const app = new Nelysia()
  .get("/", "Hello from Nelysia!")
  .get("/user/:id", ({ params }) => ({ id: params.id }))
  .post("/users", ({ body }) => body, {
    body: t.Object({ name: t.String(), email: t.String() })
  })

app.listen(3000)

1. 3-Lane AOT Execution 1. การทำงาน AOT แบบ 3 Lane

Public lanes are COMPILED, SPECIALIZED, and GENERIC. A proven compiled route uses the compiler IR/function table; specialized routes use an immutable per-route data plan; dynamic behavior falls back to the reference pipeline. Runtime eval() and new Function() never evaluate user source.

Public lane มี COMPILED, SPECIALIZED และ GENERIC โดย route ที่พิสูจน์ได้ใช้ compiler IR/function table, specialized ใช้ immutable data plan ต่อ route และ behavior แบบ dynamic จะ fallback ไป reference pipeline เสมอ ไม่มี runtime eval() หรือ new Function() เพื่อประเมิน source ของผู้ใช้

Core Philosophy & Key Concepts สถาปัตยกรรมและแนวคิดหลัก (Key Concepts)

Traditional web frameworks route all HTTP traffic through a universal, generic pipeline where every request allocates context objects, parses query parameters, resolves headers, and iterates through middleware arrays. Nelysia breaks this paradigm by introducing ahead-of-time (AOT) static route analysis.

เว็บเฟรมเวิร์กทั่วไปมักส่งทุก Request วิ่งผ่าน Pipeline รูปแบบเดียวกันหมด ซึ่งต้องจองหน่วยความจำสำหรับ Context Object, Parse ข้อมูล Query และวนลูปผ่าน Middleware เสมอ Nelysia ปฏิวัติการทำงานนี้ด้วยการใช้ระบบวิเคราะห์ Route ล่วงหน้า (AOT Static Route Analysis)

STATIC FAST PATH

Explicit static values use static-prebuilt; supported zero-argument functions use static-sync. Both bypass normal context allocation.

ค่าคงที่ใช้ static-prebuilt; ฟังก์ชันไม่มี argument ที่รองรับใช้ static-sync และทั้งคู่ข้ามการสร้าง Context ปกติ

SPECIALIZED PATH

Routes with dynamic URL parameters extract only necessary segment values without paying for unused cookie or query parsing.

เส้นทางที่มี Parameter ใน URL จะดึงเฉพาะค่าที่จำเป็น ตัด overhead จากการอ่าน Cookie หรือ Query ที่ไม่ได้ใช้ออกไป

GENERIC PATH

Dynamic routes with hooks, schemas, or opaque handlers safely retain full context, error handling, and lifecycle guarantees.

เส้นทางที่มี Hooks ซับซ้อน หรือ Schema หลายระดับ จะทำงานบน Full Pipeline ที่ปลอดภัยและยืดหยุ่นเต็มรูปแบบ

1. Method Chaining (Recommended for Type Inference) 1. การเขียนแบบ Method Chaining (แนะนำเพื่อ Type Inference)

Method chaining is the recommended style when you want TypeScript to retain the accumulated route, schema, client, and response types. Separate statements still register routes and work at runtime, but the variable keeps the type it was declared with; use the returned value or a continuous chain when you need the complete inferred route map for typed tooling.

แนะนำให้ใช้ Method Chaining เมื่อ ต้องการให้ TypeScript เก็บชนิดของ Route, Schema, Client และ Response ที่สะสมครบถ้วน การแยกเป็นหลาย statement ยังลงทะเบียน route และทำงานตอน runtime ได้ตามปกติ แต่ตัวแปรจะคง type ตอนประกาศไว้ หากต้องการ route map สำหรับ typed tooling ให้ใช้ค่าที่เมธอดคืนกลับมาหรือเขียนต่อเป็น chain เดียว

Method Chaining: Do vs Don't
// ✅ DO: Continuous method chaining preserves full type inference
export const app = new Nelysia()
  .get("/", "Home")
  .get("/user/:id", ({ params }) => params.id)
  .post("/data", ({ body }) => body)

// Separate statements still work at runtime.
const broken = new Nelysia()
broken.get("/", "Home")
broken.get("/user/:id", ({ params }) => params.id)
// Use a chain (or the returned value) when full route inference is needed.

2. Order of Code & Execution Contract 2. ลำดับของโค้ดและการทำงาน (Order of Code)

Nelysia follows a strict, predictable lifecycle execution order. Hooks like onBeforeHandle and onError attach to the app instance and intercept matching requests in deterministic registration order.

Nelysia ทำงานตามลำดับของโค้ดที่ประกาศอย่างเคร่งครัดและคาดเดาได้ โดย Hook ต่างๆ เช่น onBeforeHandle และ onError จะผูกเข้ากับแอปและดักจับคำขอตามลำดับการลงทะเบียน

Registration Order Example
const app = new Nelysia()
  // 1. This hook runs first for all incoming requests
  .onBeforeHandle(() => {
    console.log("Step 1: Auth check")
  })
  // 2. Route handler runs only after before-hooks succeed
  .get("/hello", () => {
    console.log("Step 2: Handler executed")
    return "ok"
  })
  // 3. After-hooks run on the resulting response
  .onAfterHandle((ctx, res) => {
    console.log("Step 3: Response decorated")
  })

3. Deterministic Route Resolution 3. ระบบค้นหาเส้นทางแบบ Deterministic $O(1)$

Unlike frameworks that use nested regex trees or backtracking matchers, Nelysia uses:

ต่างจากเฟรมเวิร์กทั่วไปที่ต้องวนลูป Regex หลายชั้น Nelysia ใช้สถาปัตยกรรมค้นหาเส้นทางดังนี้:

  • Static Routes: Matched via $O(1)$ hash table lookups. If a match is found, response begins immediately.
  • Dynamic Parameter Routes: Parameter segments (e.g. /users/:id) are extracted with prefix indexing, eliminating regex backtracking vulnerabilities.
  • RFC 405 Method Not Allowed: If a path exists for GET but a client calls POST, Nelysia automatically returns 405 with the Allow header listing supported methods.
  • HEAD & OPTIONS: Resolved out of the box without requiring manual boilerplate handlers.

4. Single Source of Truth 4. Schema เป็น Single Source of Truth

Instead of maintaining separate TypeScript interface definitions and runtime validation schemas, Nelysia uses schemas as the single source of truth:

แทนที่จะต้องเขียน TypeScript interface ซ้ำซ้อนกับตัวตรวจ Schema รันไทม์ Nelysia ใช้ Schema เป็น แหล่งความจริงแหล่งเดียว (Single Source of Truth):

Single Source of Truth
import { t, type Infer } from "@narudom96/nelysia"

// 1. Define schema once
export const UserSchema = t.Object({
  id: t.String(),
  name: t.String(),
  age: t.Number()
})

// 2. Infer compile-time TypeScript type automatically
export type User = Infer<typeof UserSchema>
// Resulting type: { id: string; name: string; age: number }

// 3. Use in Nelysia route with automatic runtime validation
app.post("/users", ({ body }) => {
  const user: User = body as User // 100% Guaranteed valid at runtime
  return user
}, {
  body: UserSchema
})

async function doAsyncWork(signal: AbortSignal) {
  await new Promise<void>((resolve, reject) => {
    const onAbort = () => { clearTimeout(timer); reject(signal.reason) }
    const timer = setTimeout(() => {
      signal.removeEventListener("abort", onAbort)
      resolve()
    }, 1000)
    signal.addEventListener("abort", onAbort, { once: true })
  })
}

Routing & HTTP Methods ระบบ Routing และ HTTP Methods

Nelysia features deterministic route matching. Static paths execute via direct $O(1)$ dictionary lookups. Parameter routes extract path variables. If an existing path receives an unsupported method, Nelysia returns 405 Method Not Allowed with the Allow header populated automatically. HEAD requests are resolved out of the box, while an explicit .options() handler takes precedence over automatic 204 + Allow.

ระบบ Route ของ Nelysia ทำงานอย่างแม่นยำ เส้นทาง Static ค้นหาผ่าน Hash Table ด้วยความเร็ว $O(1)$ เส้นทางที่มีพารามิเตอร์จะถูกจับคู่อย่างถูกต้อง หากมีการเรียก Method ที่ไม่ได้เปิดไว้ จะตอบกลับด้วย 405 Method Not Allowed พร้อม Header Allow อัตโนมัติ โดย HEAD รองรับในตัว และ explicit .options() handler จะทำงานก่อน automatic 204 + Allow

Route Registration
// Method chaining
app
  .get("/items", () => [{ id: 1, name: "Widget" }])
  .post("/items", ({ body }) => ({ created: true, body }))
  .put("/items/:id", ({ params, body }) => ({ id: params.id, updated: body }))
  .delete("/items/:id", ({ params }) => ({ id: params.id, deleted: true }))
  .patch("/items/:id", ({ params, body }) => ({ id: params.id, patch: body }))
  .getStatic("/health", { status: "ok" }) // 100% Context-free compiled route
  .all("/api/auth/*", async (ctx) => auth.handler(new Request(ctx.request.url, {
    method: ctx.request.method, headers: ctx.request.headers
  }))) // every HTTP method

A path ending in /* is a wildcard route: it captures every sub-path beneath its prefix, exposed as params["*"]. Wildcards must be the final segment and are always served through the generic runtime.

Path ที่ลงท้ายด้วย /* คือ wildcard route จับทุกเส้นทางย่อยภายใต้ prefix นั้น ค่าที่เหลืออยู่ใน params["*"] ต้องอยู่ตำแหน่งสุดท้ายของ path เท่านั้น และจะทำงานบน generic runtime เสมอ

Non-function values passed to .get(path, value) become precompiled static routes (context-free, standalone-eligible) — the fastest tier.

กฎของ path: ทุก path ต้องขึ้นต้นด้วย / ชื่อ parameter ต้องตรง ^[A-Za-z_][A-Za-z0-9_]*$ ลงท้ายด้วย slash (/users/) ถือเป็น route เดียวกับ /users ลงทะเบียน method + path ซ้ำจะ throw Duplicate route การส่งค่าตรงๆ (ไม่ใช่ function) ให้ .get(path, value) จะกลายเป็น static route ที่ precompile ไว้ — เร็วที่สุด

  let timer: any

      "cache-control": "no-cache",
      "connection": "keep-alive"
    }
  })
})

Unlike traditional frameworks where requests traverse an unpredictable array of middleware callbacks, Nelysia executes requests through a deterministic, strictly ordered lifecycle pipeline. Every stage has a well-defined single responsibility:

[ Request ]
    │
    ├─ 1. Await lazy modules; normalize method and URL
    ├─ 2. Resolve Fetch mount or match route

1. onBeforeHandle: Short-Circuiting Guards 1. onBeforeHandle: การทำ Guard ดักสิทธิ์ล่วงหน้า

onBeforeHandle runs after request validation but before the route handler. Returning a response from this hook halts the remaining pipeline immediately and skips handler execution. Authentication packages can register an internal route guard that runs earlier—after route matching but before parsing and validation—while ordinary permission checks and rate limits commonly use this hook:

onBeforeHandle ทำงานหลัง request validation แต่ก่อนเรียก Handler หากส่ง Response กลับ Hook นี้จะ หยุด pipeline ที่เหลือทันที และไม่เรียก Handler ส่วน authentication package สามารถลง route guard ภายในที่ทำงานเร็วกว่า—หลัง route match แต่ก่อน parse/validation—ขณะที่ permission check และ rate limit ทั่วไปมักใช้ hook นี้

Authentication Guard Pattern
app.onBeforeHandle(({ headers, response }) => {
  const token = headers.get("authorization")
  if (!token || !token.startsWith("Bearer ")) {
    // Short-circuit: response is delivered, handler NEVER executes
    return response(401, { error: "Unauthorized: Missing or invalid token" })
  }
})

Response Decoration Pattern

Best Practices & Architecture สถาปัตยกรรม & Best Practices

Nelysia is unopinionated about internal coding patterns, but for production-grade, maintainable applications, we strongly recommend a Feature-Based Modular Architecture. Separating routing controllers, business services, and data models guarantees type integrity, testability, and clean domain isolation.

Nelysia ยืดหยุ่นต่อรูปแบบการเขียนโค้ด แต่สำหรับแอปพลิเคชันระดับ Production ขนาดใหญ่ ขอแนะนำให้ใช้สถาปัตยกรรม Feature-Based Modular Architecture การแยก Controller, Service ที่ประมวลผล Business Logic และ Schema Model ออกจากกันอย่างชัดเจน จะช่วยรักษา Type Integrity ทำให้เขียน Unit Test ได้รวดเร็ว และแบ่งแยก Domain ชัดเจน

Recommended Directory Layout
src/
  modules/
    auth/
      index.ts        # Nelysia Controller: HTTP routes, cookies, validation
      service.ts      # Service: Decoupled business logic (static/class)
      model.ts        # Model: DTO validation schemas (t or Zod)
    user/
      index.ts        # User Controller
      service.ts      # User Service
      model.ts        # User Model
  shared/
    db.ts             # Database client (Drizzle / Prisma)
    config.ts         # Environment configuration
  app.ts              # Root Nelysia app: mounts domain sub-apps
  index.ts            # Server entrypoint: listen or cluster
1. CONTROLLER PATTERN

Treat each Nelysia instance as a controller. Destructure parameters and pass plain data to services; do not pass the raw Context.

ใช้อินสแตนซ์ Nelysia 1 ตัวแทน 1 Controller ดึงเฉพาะค่าที่จำเป็นส่งให้ Service หลีกเลี่ยงการส่งทั้ง Context เข้าไปใน Business Logic

2. SERVICE PATTERN

Implement domain logic in abstract class with static methods to prevent runtime class allocation and allow instant unit testing.

เขียน Business Logic ใน abstract class แบบ static เพื่อลด overhead การ allocate memory และทำให้เขียน Unit Test ได้ทันทีโดยไม่ต้องจำลอง HTTP

3. MODEL & DTO PATTERN

Define request and response shapes with t or Standard Schema (Zod/Valibot). Derive TypeScript types as a single source of truth.

สร้าง Schema กำกับ Request/Response ด้วย t หรือ Zod และดึง TypeScript Type จาก Schema โดยตรง ให้เป็น Single Source of Truth

import { HttpError } from "@narudom96/nelysia"

export abstract class AuthService {
  static async signIn(credentials: { username: string; password: string }) {
    if (credentials.username !== "admin" || credentials.password !== "secret") {
      throw new HttpError(401, "Invalid username or password")
    }
    return { id: "usr_123", token: "jwt_auth_token" }
  }
}

import { Nelysia } from "@narudom96/nelysia"

Official JWT Authentication (@narudom96/nelysia/jwt) ระบบยืนยันตัวตน JWT ทางการ (@narudom96/nelysia/jwt)

jwt<Claims>(options) (@narudom96/nelysia/jwt) provides opt-in authentication using Web Crypto HMAC-SHA256. Public routes do not inspect the Authorization header, verify a token, or build an auth payload. Protected routes use { auth: "jwt" }, { auth: true }, or { auth: { strategy: "jwt" } } and verify with the plugin instance's reused CryptoKey:

jwt<Claims>(options) (@narudom96/nelysia/jwt) เป็นระบบยืนยันตัวตนแบบ opt-in ผ่าน Web Crypto HMAC-SHA256 โดย public route จะไม่อ่าน Authorization header ไม่ verify token และไม่สร้าง auth payload ส่วน protected route ที่ใช้ { auth: "jwt" }, { auth: true } หรือ { auth: { strategy: "jwt" } } จะตรวจสอบด้วย CryptoKey ที่ plugin instance ใช้ซ้ำ:

JWT Setup & Usage
import { Nelysia } from "@narudom96/nelysia"
import { jwt, signJwt } from "@narudom96/nelysia/jwt"

const secret = process.env.JWT_SECRET
if (!secret) throw new Error("JWT_SECRET is required")

const app = new Nelysia()
  .use(jwt({
    secret,
    expiresIn: 3600
  }))
  // 1. Public route: 0 auth overhead
  .get("/public", () => ({ status: "open" }))

  // 2. Protected route: verify token & access context.auth
  .get("/profile", ({ auth }) => ({ status: "authenticated", user: auth }), { auth: "jwt" })

  // 3. Sign token on login
  .post("/login", async () => {
    const token = await signJwt({ sub: "user-1", role: "admin" }, process.env.JWT_SECRET!)
    return { token }
  })

Zero-Port Testing with app.inject() การทดสอบแบบ Zero-Port ด้วย app.inject()

app.inject(options) executes in-memory HTTP requests directly against your application pipeline without opening or binding a network port. This guarantees lightning-fast unit and integration tests with zero port collision:

app.inject(options) จำลอง HTTP Request ตรงเข้าไปยัง Application Pipeline ในหน่วยความจำโดยไม่ต้องเปิดหรือแย่ง Network Port ใดๆ เหมาะสำหรับการเขียน Unit และ Integration Tests ที่รวดเร็ว:

Testing with app.inject
const res = await app.inject({
  method: "GET",
  path: "/users/42",
  query: { filter: "active" }
})

console.log(res.statusCode) // 200
console.log(await res.json()) // { id: "42", filter: "active" }
console.log(await res.text()) // text string
console.log(await res.bytes()) // Uint8Array

Client SDK (`@narudom96/nelysia/client`) Client SDK (`@narudom96/nelysia/client`)

Nelysia provides a lightweight, type-friendly client library (under 2KB) similar to Elysia's Eden, designed to connect your frontend and backend with end-to-end type safety without code generation:

Nelysia มีไลบรารี Client ขนาดกะทัดรัด (ไม่ถึง 2KB) ในรูปแบบเดียวกับ Eden ของ Elysia ช่วยเชื่อมต่อระหว่าง Frontend และ Backend ด้วย End-to-End Type Safety แบบไม่ต้องพึ่ง Code Generation:

Client SDK Usage (Frontend / Browser)
import { createClient } from "@narudom96/nelysia/client"

const api = createClient("http://localhost:3000")

// GET with typed response
const { data, error, response } = await api.get<{ id: string; name: string }>("/users/42")

if (error) {
  console.error(`API Error: \${error.status}`, error.body)
} else {
  console.log(`User: \${data?.name}`)
}

// POST with typed payload
await api.post("/users", { name: "Alex", age: 28 })

// PUT, DELETE, and generic request method
await api.put("/users/42", { age: 29 })
await api.delete("/users/42")
await api.request<{ ok: boolean }>("PATCH", "/users/42", { age: 30 })

Response Structure: Every call resolves to { data?, error?, response }: data is populated with parsed JSON when response.ok is true. On failure, error is populated with { status, body }, and the native Web Standard response is always accessible. Non-JSON bodies resolve data to undefined instead of throwing unexpected exceptions.

โครงสร้าง Response: ทุกคำขอจะได้ผลลัพธ์เป็น { data?, error?, response }: เมื่อสำเร็จ (response.ok) data จะมี JSON ที่ parse แล้ว หากเกิดข้อผิดพลาด error จะมี { status, body } และยังเข้าถึง Web Standard response ดั้งเดิมได้เสมอ หาก body ไม่ใช่ JSON จะได้ data เป็น undefined โดยไม่โยน error ออกมาให้โปรแกรมพัง

Route-aware Client
import { createClient, createTypedClient } from "@narudom96/nelysia/client"
import type { app } from "../src/app"
import type { NelysiaRoutes } from "./nelysia-routes"

const result = await typedApi.get("/users/42")

else console.log(result.data)

// Generated or manually declared maps still use the compatibility API.
const mappedApi = createTypedClient<NelysiaRoutes>("http://localhost:3000")

Adapter generation (the default when standalone does not apply) also benefits from the compiler: the Node, Bun, and Fetch adapters serve hook-free GET routes through the shared compiled dispatcher — pre-serialized static payloads, prefix matching, and per-method lookup — while hooks, schemas, and other methods fall through to the generic router. The manifest records this with dispatcher: true and an NELY003 info diagnostic reporting fast-path coverage.

Adapter generation (ค่าเริ่มต้นเมื่อไม่เข้า standalone) ก็ได้ประโยชน์จากคอมไพเลอร์เช่นกัน: adapter ของ Node, Bun และ Fetch จะ serve GET ที่ไม่มี hook ผ่าน compiled dispatcher ตัวเดียวกัน — payload ที่ serialize ล่วงหน้า, prefix matching และ lookup แยกตาม method — ส่วน hooks/schemas/method อื่นตกไป generic router manifest บันทึกด้วย dispatcher: true และ diagnostic NELY003 ที่รายงาน coverage ของ fast path

Lifecycle and execution rulesกฎ Lifecycle และการทำงาน

For a matched HTTP route, Nelysia awaits lazy modules, normalizes the request, creates context, runs request hooks, applies internal auth guards, parses the body, validates request fields, runs context extensions and transform/before hooks, executes the handler, validates the response, maps and finalizes it, then runs after-response hooks.
